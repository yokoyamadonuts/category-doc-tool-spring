# 0005 経路探索を DB ではなくドメインで行う

2026-10-23 採用

## 状況

文書から文書への経路を探す。MySQL の再帰共通テーブル式でも、読み込んだモデルをアプリで探しても書ける。既存版は Neo4j に保存し、探索はドメインの関数で行っていた。

## 決定

プロジェクトを丸ごと読み込み、`domain` の純粋な関数で探す。最短経路は幅優先探索、全経路も幅優先で伸ばし、深さ5、最大20本で打ち切る。恒等射はたどらない。

## 理由

- 1つのプロジェクトの文書は多くて数百で、丸ごと読んでも軽い
- 循環を避けつつ全経路を数え上げ、上限で打ち切る処理は、再帰共通テーブル式では書きにくく読みにくい
- 純粋な関数なら、DB なしの単体テストで境界の場合まで確かめられる
- 幅優先なら見つかる順がそのまま短い順になり、20本で打ち切っても短い経路が残る。既存版は深さ優先で数え上げてから並べ替えており、本数の上限を足すと、途中で打ち切ったときに短い経路を取りこぼしうる

## 結果

- 経路を探すたびにプロジェクトを丸ごと読む。文書が数万になれば見直す
- 検証と追跡の表も同じく、保存せず毎回ドメインで計算する

## 採らなかった案

- MySQL の再帰共通テーブル式: 上のとおり
- 探索の結果を保存する: 取り込んだ後に変わらないので可能だが、いまの大きさでは要らない
