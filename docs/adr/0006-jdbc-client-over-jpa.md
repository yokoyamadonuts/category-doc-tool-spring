# 0006 保存を JPA ではなく JdbcClient で行う

2026-10-23 採用

## 状況

第1段階では、プロジェクトの一覧を Spring Data JPA で読んでいた。第3段階で、カテゴリ、文書、射、関手、関手の対応、自然変換、自然変換の成分の7つの表を足した。

## 決定

Spring Data JPA をやめ、JdbcClient で読み、`JdbcTemplate.batchUpdate` でまとめて入れる。SQL は `JdbcProjectRepository` の1か所に置く。

## 理由

- グラフは取り込みのときに一度に入れ、読むときは丸ごと読む。エンティティの状態の管理や遅延読み込みの出番がない
- ドメインのモデルは不変の record で、JPA のエンティティにすると、対応づけのためだけの可変なクラスが7つ増える
- 入れる順と読む順を SQL で明示でき、外部キーの向きに合わせた順で入れられる
- JPA と JDBC を混ぜると、JPA が書き出す前に JDBC が参照して外部キーで落ちる、といった順の問題が起きうる

## 結果

- 対応づけのコードを手で書いた。1つのクラスに収まっている
- 次の2つは、試して分かったことに合わせて決めた
  - `metadata` は JSON 型ではなく文字列の列に入れる。MySQL の JSON 型はキーの順を並べ替え、YAML に書いた順を保てない
  - 外部キーは各表から `projects` への1本だけにし、`ON DELETE CASCADE` で削除を連鎖させる。カテゴリから関手へのように連鎖の経路が複数あると、MySQL 9.7 で関手の行が消え残った。表どうしの参照は取り込みで確かめる

## 採らなかった案

- Spring Data JPA を続ける: 上のとおり
- Spring Data JDBC: 集約を1つの表の木として扱う前提で、関手の対応のように複数のカテゴリにまたがる参照と合わない
- jOOQ: 型の付いた SQL は魅力だが、表が7つ、問い合わせが10ほどでは、コード生成の仕組みを足す手間に見合わない
