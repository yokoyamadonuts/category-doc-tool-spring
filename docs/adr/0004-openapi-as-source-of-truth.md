# 0004 API は仕様書を正本にし、生成せずに比べる

2026-10-23 採用

## 状況

API の仕様と実装をそろえる方法は3つある。仕様書からサーバーのコードを生成する、実装から仕様書を生成する、両方を手で書いて比べる。

## 決定

`openapi/openapi.yaml` を正本にする。

- サーバー: コントローラーは手で書く。springdoc が実装から出力する仕様と `openapi.yaml` を契約テストで比べ、パスとメソッドの組、各操作の成功時の状態コードがずれたら落とす
- 画面: `openapi-typescript` で型だけを生成し、`openapi-fetch` で呼ぶ

## 理由

- 仕様書を先に書くと、画面とサーバーの作業を同じ約束から始められる
- サーバーのコードを生成すると、生成されたインターフェースに実装が縛られ、Spring の書き方から外れやすい
- 実装から仕様書を生成すると、実装の都合がそのまま仕様になり、説明や例を書く場所が散る
- 型だけの生成なら、画面のコードの書き方は縛られない

## 結果

- 契約テストが見るのは、操作の有無と成功時の状態コードまで。応答のスキーマの差は見ていない。スキーマのずれは、結合テストと E2E で応答の中身を確かめて防いでいる
- 契約テストは、仕様書に存在しない操作を1つ足すと落ちることと、成功時の状態コードを変えると落ちることを確かめた
- `openapi-typescript` 7.13 は TypeScript 5 を peer に求め、7 と同居できない。依存に入れず、`npm run gen:api` で TypeScript 5.9 と一緒に npx で動かす

## 採らなかった案

- OpenAPI Generator でサーバーを生成する: 上のとおり、実装が生成物に縛られる
- springdoc の出力を正本にする: 上のとおり、仕様が実装の後追いになる
